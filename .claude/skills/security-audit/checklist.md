# Security checklist: Laravel / Filament / Livewire

Each section lists what to check, then the commands that surface candidates. A grep hit is only a lead. Verify every lead using step 4 of SKILL.md.

## 1. Authentication & panel access
- Does `User` implement `FilamentUser::canAccessPanel()`, and does it actually restrict access? If it's missing, **any** user row can log into `/admin` in production. Is there a role or flag (`is_admin`, `role`) and is it enforced?
- User management (`app/Filament/Resources/Users/`): can a non-privileged admin create admins, change their own role, delete the last admin, or edit another user's password without proper rules? Are password rules (`Password::defaults()`) and hashing (`'hashed'` cast) in place?
- Login throttling on the Filament login. Password reset flow. Session fixation on login, which Laravel handles by default; confirm it wasn't overridden.
- The `/login` redirect, and the `auth` middleware on CV routes. Check that it uses the same guard as the panel.
```bash
grep -rn "canAccessPanel\|FilamentUser\|->authMiddleware\|->login(" app/
grep -rn "is_admin\|role" app/Models/User.php database/migrations/
```

## 2. Authorization / IDOR
- CV preview and download routes (`/admin/applicants/{applicant}/cv/...` and `/admin/talent-pool/{entry}/cv/preview`): any authenticated user can fetch any CV by ID. Is that intended? Check for sequential IDs versus UUIDs, and for policies.
- Filament resources: is `canViewAny`, `canEdit` or `canDelete` defined, or is everything allowed by default? Do custom Actions (`SendRejectionEmailAction`, `UpdateStatusAction`, `ApplicantCvActions`) check authorization, or only hide their buttons? A hidden button can still be invoked through a Livewire call.
- Livewire: public properties that hold IDs or models can be tampered with from the client. Look for `#[Locked]` where it's needed.
```bash
grep -rn "authorize\|Gate::\|->can(\|policy\|#\[Locked\]" app/
ls app/Policies 2>/dev/null
```

## 3. File upload & CV handling (highest-risk area in this app)
- Validation in `VacancyApplicationController@store` and `TalentPoolController@store`: `mimes:`/`mimetypes:` (real content sniffing, not only the extension), `max:` size, and a `file` rule. Reject `html`, `svg`, `xml` and polyglots.
- Storage: is the stored path generated by the server (`store()` / `hashName()`) rather than taken from the client filename? Is the file stored on a **private** disk, never under `public/` or `storage/app/public`? Check `config/filesystems.php` `cv_disk` and the S3 visibility.
- `CvStorage::readDisk($path)` takes a path from the DB. Could a path containing `../` or an absolute path ever reach it, through mass assignment, an import, or an admin edit?
- Preview response: inline rendering of attacker-controlled content inside the admin origin leads to **stored XSS against HR**. You need `Content-Type` taken from an allowlist (not the client mime), `Content-Disposition: attachment` for anything that isn't a PDF, `X-Content-Type-Options: nosniff`, and ideally a `Content-Security-Policy: sandbox` on the preview.
- The download filename header: does it come from user input? Check for header injection or a non-ASCII filename.
```bash
grep -rn "store(\|storeAs(\|putFile\|getClientOriginalName\|getClientMimeType\|mimes:\|mimetypes:\|->file(" app/
grep -rn "response()->file\|->download(\|Content-Disposition\|Content-Type" app/
```

## 4. Injection
- SQL: `DB::raw`, `whereRaw`, `orderByRaw`, `selectRaw`, `havingRaw`, `DB::statement`/`select` with interpolated variables, and dashboard widgets building SQL by hand. Check sortable or searchable columns that take a column name from the request.
- Command or code execution: `exec`, `shell_exec`, `system`, `proc_open`, `passthru`, backticks, `eval`, `unserialize` on user data, and `Process::run` with interpolated input.
- Template injection: `Blade::render` or `view()` with user-controlled template strings.
```bash
grep -rnE "Raw\(|DB::(raw|statement|select|unprepared)" app/ database/ routes/
grep -rnE "\b(exec|shell_exec|system|passthru|proc_open|popen|eval|unserialize)\(|Process::" app/ routes/
```

## 5. XSS & output encoding
- Unescaped Blade output with `{!! !!}`: what flows into it? Job descriptions written by admins in a rich editor and rendered publicly are probably intended, but are they sanitized? Applicant-supplied fields must **never** be unescaped.
- Filament: `->html()`, `HtmlString`, `->formatStateUsing(fn) => new HtmlString(...)`, `->markdown()`, `->description()` with applicant data. Infolists and tables in the admin panel are an XSS-on-HR vector.
- Rejection email (`app/Mail/ApplicantRejected.php` and its view): could HR feedback or an applicant name inject HTML into the email?
- JSON-LD and SEO meta (`SeoTest` suggests they exist): `@json` versus manually echoed JSON in `<script>` tags, which can break out with `</script>`.
```bash
grep -rn "{!!" resources/views/
grep -rn "HtmlString\|->html()\|->markdown()\|toHtml\|e(" app/Filament app/Mail
grep -rn "application/ld+json" -A5 resources/views/
```

## 6. Mass assignment & validation
- `$guarded = []` or broad `$fillable` on `Applicant`, `TalentPoolEntry` and `User`. Can the public apply form set `status`, `job_id`, `cv_path`, `hr_feedback`, or any `*_at` timestamp? Check `Model::unguard()` in `AppServiceProvider`.
- `$request->all()`, `->fill($request->...)`, or `create($request->input())` without `validated()`/`safe()`.
- `ScreeningForm`: dynamic questions. Are the answers validated against the defined questions and their types, and is size bounded?
- Slug lookups (`/vacancies/{slug}`): does applying to an **inactive** or closed job succeed?
```bash
grep -rn "\$guarded\|\$fillable\|unguard" app/
grep -rn "->all()\|->input()\|->fill(\|::create(\$request" app/Http
```

## 7. CSRF, rate limiting, abuse
- CSRF is on by default for the `web` group. Check `bootstrap/app.php` for `validateCsrfTokens(except: ...)`.
- `throttle:10,1` on the public POSTs: is it keyed by IP behind a proxy? If `TrustProxies` is misconfigured, every request shares one IP (a self-DoS) or the IP is spoofable via `X-Forwarded-For`. Check `trustProxies(at: ...)`.
- Duplicate or spam applications, uploads that fill the disk, and email bombing through any action that sends mail to an attacker-supplied address.
- Mail header injection through name or email fields.
```bash
grep -rn "validateCsrfTokens\|trustProxies\|trustHosts\|throttle\|RateLimiter" bootstrap/ app/ routes/
```

## 8. Sensitive data exposure & privacy
- `$hidden` on models that serialize (Livewire, JSON, logs). Password hash and remember token.
- Logging of request payloads or PII (`Log::` with `$request->all()`, CV paths, emails). Check `config/logging.php` for channels and level.
- Error pages: `APP_DEBUG` must be `false` in `.env.production.example` and Docker. With Ignition or the debug page in production, environment variables leak.
- `sitemap.xml` and public pages must not list inactive jobs or applicant data. `NoIndex` should cover the admin pages and the apply pages.
- Retention: talent pool and applicant PII with no deletion path. Report this as hardening or compliance (Indonesian PDP law), not as a vulnerability.
```bash
grep -rn "Log::\|logger(\|info(\|dd(\|dump(\|ray(" app/ routes/
grep -n "APP_DEBUG\|APP_ENV\|LOG_LEVEL" .env.example .env.production.example Dockerfile compose.production.yaml docker -r
```

## 9. Session, cookies, headers, transport
- `config/session.php`: `secure` (`SESSION_SECURE_COOKIE`), `http_only`, `same_site`, `encrypt`, and the driver.
- `APP_URL` and `URL::forceScheme('https')` behind a proxy. HSTS.
- Security headers: CSP, `X-Frame-Options`/`frame-ancestors` (clickjacking on `/admin`), `Referrer-Policy`, `Permissions-Policy`. Check for middleware or web server config in `docker/`.
- CORS config (`config/cors.php`), if present.
```bash
grep -rn "secure\|same_site\|http_only\|encrypt" config/session.php
grep -rn "forceScheme\|X-Frame-Options\|Content-Security-Policy\|Strict-Transport" app/ bootstrap/ docker/
```

## 10. Secrets & configuration
- Committed secrets: real-looking values in `.env*.example`, `compose*.yaml`, `deploy.sh`, `.github/workflows/`, `config/*.php` defaults (for example `env('X', 'real-secret')`), and `.hallmark/`. Check git history too.
- `APP_KEY` must never be committed. If it's ever exposed, cookie and session forgery and decryption of encrypted casts become possible.
- `.dockerignore` must exclude `.env`, `.git` and `storage/` so secrets aren't baked into the image.
```bash
git log -p --all -S "APP_KEY=base64" -- . ':!vendor' | head -40
grep -rnE "(password|secret|key|token)\s*[=:]\s*['\"]?[A-Za-z0-9/+_-]{12,}" --include="*.yml" --include="*.yaml" --include="*.sh" --include="*.example" --include="*.php" . 2>/dev/null | grep -v vendor/ | grep -v "env("
cat .dockerignore
```

## 11. Container & deploy
- Dockerfile: does the process run as root? Are build tools or composer dev deps left in the production image (`composer install --no-dev`)? Are base images pinned? Is the writable surface limited to `storage/` and `bootstrap/cache`?
- Compose: database or Redis ports published to `0.0.0.0`, default DB passwords, `restart` policies, and whether volumes expose the code.
- PHP config: `expose_php=Off`, `display_errors=Off`, `upload_max_filesize` consistent with the validation `max:`.
- `deploy.sh`: `curl | bash`, unquoted variables, secrets on the command line.
- CI (`.github/workflows/`): `permissions:` least privilege, pinned actions (already SHA-pinned, so keep it that way), `pull_request_target` misuse.

## 12. Dependencies
- `composer audit` and `npm audit --omit=dev` output. Report only advisories affecting code paths this app uses, and give the fixed version.
- Version constraints that allow known-vulnerable ranges.
- `livewire/blaze` and other pre-1.x or new packages: note them as a supply-chain watch item only.
